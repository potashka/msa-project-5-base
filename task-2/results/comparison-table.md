# Comparison table: price-list batch processing

## Context

Задача TradeWare: каждый день в 06:00 формировать кастомные CSV/XLS-прайс-листы для B2B-клиентов на основе PostgreSQL. Объем данных небольшой:

- `products`: 5 000-10 000 строк;
- `categories`: 50-200 строк;
- `clients`: 100-500 строк;
- `client_prices`: 10 000-20 000 строк.

Обработка простая: выполнить SQL JOIN, сформировать файл, сохранить результат и отдать статус выполнения в наблюдаемость Kubernetes.

## Comparison

| Критерий | Spring Batch | Apache Airflow | K8s Job / CronJob | Apache Spark |
|---|---|---|---|---|
| Наличие CRON-расписания | Нет встроенного CRON как платформенной функции. Обычно нужен Spring Scheduler, Quartz, Airflow, Kubernetes CronJob или внешний scheduler. | Есть расписание DAG по CRON, развитая модель запусков и retry. | Есть нативное расписание `CronJob` с CRON-выражением, например `0 6 * * *`. | Сам Spark не является scheduler. Нужен Airflow, Spark Operator, Kubernetes CronJob или managed scheduler. |
| Сложность реализации логики обработки | Удобен для chunk-oriented processing, retries, readers/writers. Для простого SQL JOIN и CSV может быть избыточен. | Логику можно описать DAG-ом, но для одной простой операции появляется лишний orchestration слой. | Минимальная: один контейнер `price-list-exporter` выполняет SQL, генерирует CSV/XLS и завершает работу. | Для простого JOIN и выгрузки слишком тяжелая модель. Потребуется Spark job, зависимости и настройка кластера/оператора. |
| Ресурсоемкость | Средняя. Нужен JVM-процесс на время batch job. Постоянная платформа не обязательна, если запускать как контейнер. | Высокая для этой задачи: webserver, scheduler, metadata DB, workers/executors. | Низкая. Pod появляется только на время выполнения job и затем завершается. | Высокая. Требуются driver/executors и ресурсы распределенной обработки, которые не оправданы объемом данных. |
| Масштабируемость и сложность реализации | Хорошо масштабируется для сложных batch-процессов, partitioning и restartability. Реализация сложнее, чем простой exporter. | Хорошо масштабируется как orchestration платформа, особенно для многих DAG и зависимостей. Для одной job сложность выше пользы. | Масштабируется горизонтально через ресурсы Kubernetes, лимиты, отдельные CronJob по сегментам клиентов, очереди или shard-параметры. Реализация простая. | Отлично масштабируется на большие данные, но сложность реализации и эксплуатации высокая. Для десятков тысяч строк не нужна. |
| Сложность развертывания в облаке и интеграция с микросервисной архитектурой | Хорошо разворачивается как контейнер, но нужен отдельный scheduler или запуск через Kubernetes. | Требует полноценного развертывания Airflow или managed-сервиса. Хорошо интегрируется, но это отдельная платформа. | Нативно подходит для Kubernetes: Docker image, ConfigMap, Secret, ServiceAccount, CronJob, logs/events/status через API кластера. | Требуется Spark on Kubernetes, Dataproc/EMR или Spark Operator. Интеграция мощная, но инфраструктурно тяжелая. |
| Интеграция с логированием и мониторингом | Логи приложения и Micrometer/Prometheus возможны, но их нужно настроить в приложении и runtime. | Есть UI, история запусков, логи, SLA/alerts, интеграции со StatsD/Prometheus. | Нативные Kubernetes logs/events/job status, интеграция с Prometheus/Grafana и централизованным логированием через стандартный стек кластера. | Есть Spark UI, event logs и метрики, но мониторинг сложнее и рассчитан на распределенные вычисления. |

## Conclusion

Для Task 2 оптимален **Kubernetes CronJob**.

Причины:

- задача маленькая по объему данных;
- запуск строго регулярный, один раз в день в 06:00;
- нет сложного ETL, зависимостей между этапами, ML или больших распределенных расчетов;
- инфраструктура уже ориентирована на облако и Kubernetes;
- CronJob позволяет запускать контейнер только на время работы, использовать Secret/ConfigMap, лимиты ресурсов, retry/backoff, `concurrencyPolicy: Forbid`, стандартные логи и метрики кластера.

Spring Batch, Airflow и Spark остаются полезными для более сложных сценариев, но для текущей задачи они добавляют лишнюю платформенную и эксплуатационную сложность.
